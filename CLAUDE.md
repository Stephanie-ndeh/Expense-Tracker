# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Reckon" — a single-user expense/lending/savings tracker built as an installable PWA, backed by Supabase (Postgres + email/password auth). Everything — wallets, transactions, categories, people, and the currency/display-name profile — lives in Supabase, scoped per-user via Row Level Security (`supabase/schema.sql`); `localStorage` holds nothing anymore. See `README.md` for the product description.

## Commands

```bash
npm install
npm run dev       # vite dev server
npm run build     # vue-tsc -b (typecheck, project-references build) then vite build
npm run preview   # serve the production build locally
npm run lint      # eslint . (flat config in eslint.config.js)
npm run format    # prettier --write . (config in .prettierrc.json)
```

There is no test suite — `npm run build` (via `vue-tsc -b`) is the strictest correctness check available: `noUnusedLocals`, `noUnusedParameters`, and `noFallthroughCasesInSwitch` are all enabled in `tsconfig.app.json`, so unused variables/params fail the build, not just warn. `npm run lint`/`npm run format` catch style/correctness issues `vue-tsc` doesn't (e.g. unused-but-typed-away mistakes, Vue template rule violations). Run `format`, then `lint`, then `build`, in that order, before every commit — see "Git workflow" below.

**Vue template pitfall**: an inline event handler with more than one statement (e.g. `@click="a = 1\nb = 2"`) relies on semicolons as statement separators; this repo's Prettier config has `"semi": false`, which strips those semicolons from template expressions too and breaks the Vue compiler. Avoid multi-statement inline handlers — call a method defined in `<script setup>` instead (e.g. `@click="cancelDelete"` with `function cancelDelete() { ... }`), which is immune to this and matches the existing style in `AddEntry.vue`/`App.vue`.

## Git workflow

Each phase/task gets its own feature branch off `develop` — never commit directly to `develop` or `master`.

1. `git checkout develop && git pull`, then `git checkout -b <phase-name>` (e.g. `phase-1-swipe-actions`).
2. Implement the phase.
3. Before committing, run in order and fix everything: `npm run format`, `npm run lint`, `npm run build`.
4. Commit the phase's changes on the feature branch.
5. Push the feature branch (`git push -u origin <phase-name>`) — do not merge it.
6. The user merges the branch into `develop` manually on GitHub.
7. Once merged, `git checkout develop && git pull` to sync before starting the next phase's branch.

## Architecture

**State: module-level reactive singletons, not Pinia.** There is no state-management library dependency. `useLedger.ts`, `useWallets.ts`, `useCategories.ts`, `usePeople.ts`, `useAuth.ts` and `useSettings.ts` all follow the same shape: a `reactive()` object created once at module scope, and the exported `use*()` function just returns computed/methods closing over that shared state. Every component that calls `useLedger()` shares the _same_ transactions array — there is no per-instance state and no store plugin. All four are now a pure in-memory mirror of Supabase — nothing is written to `localStorage`.

**Data lives entirely in Supabase.** `profiles`, `wallets`, `categories`, `people`, and `transactions` tables (`supabase/schema.sql`) are the sole source of truth, scoped per-user via Row Level Security. Every mutation in `useLedger.ts`/`useWallets.ts`/`useSettings.ts` (`addTransaction`, `removeTransaction`, `updateTransaction`, `markSettled`, `addWallet`, `renameWallet`, `removeWallet`, `updateCurrency`) is `async`: it awaits the Supabase call first and only updates local reactive state on success, then throws on failure so the calling component can surface an error (see `AddEntry.vue`, `WalletTabs.vue` for the try/catch + inline-error-text pattern). `useSync.ts` owns the login/logout lifecycle: `loadAll()` fetches everything fresh from Supabase (wallets and transactions filtered to `deleted_at is null`, plus the profile via `useSettings.ts`'s `loadProfile()`) and **replaces** local state outright (no merge — the server is authoritative), called on sign-in and then on focus/online; `clearAll()` empties local state — including resetting currency back to the default — on sign-out. That sign-out clear is what prevents one account's data from bleeding into the next account signed into the same browser.

**Soft delete, not hard delete.** `transactions` and `wallets` have a `deleted_at timestamptz` column (`supabase/migrations/004_soft_delete.sql`). `removeTransaction`/`removeWallet` `UPDATE … SET deleted_at = now()` instead of `DELETE`, then splice the row out of local state; `useSync.ts`'s `loadAll()` is what keeps soft-deleted rows out of the app by filtering `.is('deleted_at', null)` on every fetch. Any new query against these tables must apply the same filter, or deleted rows will reappear.

**IDs and timestamps**: new `wallets`/`transactions` ids are generated client-side with `crypto.randomUUID()` (the `id` columns stay plain `text`, so pre-existing non-UUID ids are untouched). `created_at` is `timestamptz` in the database (the original bigint epoch-ms columns were renamed to `created_at_ms` and kept as an untouched fallback — see `supabase/migrations/007_timestamptz_created_at.sql`); the app still works with it as a epoch-ms `number` everywhere else — `rowToTransaction`/`rowToWallet` convert the ISO string to a number on read (`new Date(r.created_at).getTime()`), and the insert helpers convert back on write (`new Date(t.createdAt).toISOString()`).

**Categories & people**: `categories` (`id`, `user_id`, `name`, `kind: 'expense' | 'income'`) and `people` (`id`, `user_id`, `name`, `phone`) are separate tables, each with a case-insensitive unique name per user (per `kind` for categories), managed by `useCategories.ts`/`usePeople.ts` — the same module-level-singleton shape as `useWallets.ts`, loaded/cleared by `useSync.ts` alongside everything else. `transactions.category_id`/`person_id` are nullable foreign keys; `label` is still what's displayed and what `personSummaries`/`owedToYou`/`categoryBreakdown` group by in `useLedger.ts`, but it's now always resolved to a category/person's canonical spelling (see below), so same-ish labels no longer split into separate buckets by casing.

**Category/person find-or-create** (`AddEntry.vue`): the category field (expense/income) and the person field (lend/repay) are plain `<input list="...">` elements backed by a `<datalist>` of suggestions — `useLedger.ts`'s `suggestedCategories(kind)`/`suggestedPeople()` return that type's categories/people sorted most-used-first, counted from `category_id`/`person_id` occurrences in `state.transactions` (not full-text label matching). On submit, the typed text is resolved via `useCategories.ts`'s `findOrCreateCategory(name, kind)` / `usePeople.ts`'s `findOrCreatePerson(name)`: a case-insensitive match against the already-loaded local list first (no network round-trip), falling back to an insert (racing a duplicate-key error is handled by re-querying rather than throwing, since this is "find or create", not a user-facing duplicate check) — the resolved row's `id` and canonical `name` are what get saved as `categoryId`/`personId` and `label`. `save`/`withdraw` labels remain plain free text, untouched by any of this.

**Integrity constraints** live in `supabase/migrations/005_integrity_constraints.sql`, `006_amount_positive_check.sql`, and `010_transfers.sql`: a composite FK ties `transactions(wallet_id, user_id)` to `wallets(id, user_id)`; `transactions.type` has a `check` listing the current `TransactionType` values — **adding a new transaction type requires a migration that drops and recreates `transactions_type_check`** with the wider list, or inserts will fail; `transactions.amount` must be `> 0`; a partial unique index guarantees at most one `is_default = true` wallet per user (excluding soft-deleted ones); and a `check` ties `transfer_id`'s presence exactly to `type in ('transfer_out', 'transfer_in')`.

**Domain model** (`src/types/transaction.ts`): a single `Transaction` shape covers eight transaction types (`expense`, `income`, `lend`, `repay`, `save`, `withdraw`, `transfer_out`, `transfer_in`). `TYPE_META` is the lookup table that drives everything derived from a type: display verb, sign (+1/-1) for balance math, the placeholder hint for the `label` field, and which `group` (`cash` | `lending` | `savings` | `transfer`) it belongs to. Adding a new transaction type means extending this union and `TYPE_META`, not branching on the type string elsewhere — most of `useLedger.ts` is written generically against `TYPE_META[t.type].sign/group`.

**Transfers between wallets**: a transfer is two ordinary `transactions` rows — one `transfer_out` (sign `-1`) on the source wallet, one `transfer_in` (sign `+1`) on the destination wallet — sharing a `transfer_id`. This is why `balance` just adds `+ transfer_sum` as one more group term, the same way `lending` is added: whichever leg is in scope for the active wallet correctly moves that wallet's balance, and when both legs are in scope (the 'All' view) they cancel to zero with no special-case code. Each leg's `label` is the _other_ wallet's name (set programmatically by `addTransfer()`, never typed by the user). `monthlyTrend`/`categoryBreakdown`/`monthComparison`/`thisMonthSpend` only match specific other types, so transfers are automatically excluded — no filtering code needed for that. `useLedger.ts`'s `addTransfer()`/`updateTransfer()`/`transferSibling()` are the transfer-specific API (wallets aren't reassignable via `updateTransfer` — delete and recreate instead); `removeTransaction()`/`markSettled()` are transfer-aware internally (they check the row's `transferId` and, if set, act on both rows via a single `.eq('transfer_id', id)` statement instead of `.eq('id', id)`), so every existing call site keeps working unchanged. Pairing integrity has no traditional FK (there's no parent table to point at — just two sibling rows) — it's enforced by a CHECK constraint (`transfer_id` presence) plus doing the multi-row writes as single atomic Postgres statements (one bulk `.insert([outRow, inRow])` for creation, one grouped `.update(...).eq('transfer_id', id)` for edit/delete) rather than two independent calls. `AddEntry.vue` shows "Transfer" as one type option with its own From/To-wallet sub-form; editing a transfer shows its wallets as read-only (can't reassign) with amount/date/note/planned still editable, and switching an existing entry's type into/out of `'transfer'` is disabled via `canSelectType()`.

**Wallets** (`src/types/wallet.ts`): every transaction has a `walletId`; `WalletTabs.vue` is the horizontal-scroll tab bar ('All' + one pill per wallet, each with a "✎" rename icon and, for non-default wallets, a "×" delete icon) that drives the shared `activeWalletId` ref, which every `useLedger()` consumer filters against. Exactly one wallet per user has `isDefault: true` (auto-created as "Personal" by `useSync.ts`'s `loadAll()` the first time a user's wallet list comes back empty) — it can be renamed but can't be deleted. `addWallet`/`renameWallet`/`removeWallet` in `useWallets.ts` enforce, respectively: no duplicate names per user (case-insensitive, backed by a unique index in `supabase/schema.sql` as well as a client-side check — `renameWallet` excludes the wallet's own id from that check), the same duplicate-name rule when renaming (requires the `wallets_update_own` RLS policy from `supabase/migrations/001_wallets_update_policy.sql`), and no deleting a wallet that still has transactions in it (blocked, not cascaded — the user has to empty it first).

**Profile/currency** (`useSettings.ts`): `settings.currency` is now backed by the `profiles` table (`id = auth.users.id`, one row per user, lazily created defaulting to `'FCFA'` the first time `loadProfile()` runs with no existing row) instead of `localStorage`. The currency `<input>` in `App.vue` still uses `v-model` for snappy typing, but only persists on `@change` (blur/commit) via `updateCurrency()` — not on every keystroke — since each save is now a network round-trip; a failed save surfaces inline via `currencyError` in `App.vue` without reverting the input.

**`planned` is the "hasn't happened yet" flag**, not a separate list — a transaction is either `settled` (`!planned && date <= today`) or `upcoming` (`planned || date > today`). Balance, savings, and monthly aggregates are all computed only from `settled`; `upcoming` feeds the "coming up" UI. Keep this filter (not a boolean split into two arrays) when adding new derived views.

**`useLedger()` is the single source of derived data** — balance, savings, per-person owed amounts, monthly trends, category breakdowns, month-over-month comparisons, search/filtering, and JSON export/import all live here as computed properties or functions over the one `state.transactions` array. Components (`BalanceHero`, `SummaryCards`, `TrendChart`, `PeopleView`, `TrendsView`, `AllActivityView`, `RecentActivity`, etc.) are thin — they call into this composable rather than recomputing aggregates themselves. When adding a new summary/view, prefer adding a computed/function here over duplicating filter/reduce logic in a component.

**Search/filter** (`AllActivityView.vue`): `filterActivity(filters)` in `useLedger.ts` is deliberately unscoped by the shared `activeWalletId` — it filters over every settled transaction regardless of the home screen's active wallet tab, with `walletId` as just one of its own explicit filter fields (`query` substring-matches `label`/`note`; `type`/`walletId`/`label` are exact matches, `'all'` meaning unfiltered; `label` is matched against the merged, deduped set of category + people names, not free text). `activityTotal(items)` sums `TYPE_META[type].sign * amount` over whatever's currently filtered. The view's Week/Month/Year/All buttons and its two manual date inputs both just set the same `startDate`/`endDate` refs — there's one date-range concept with two ways to set it, not two separate filters.

**`App.vue` is a hand-rolled router**: a single `view` ref (`'home' | 'activity' | 'trends'`) switches between full-screen views; modals (`AddEntry`, `PeopleView`, the inline settings panel) are boolean-flag overlays rather than routes. There's no vue-router. Ahead of the router, `App.vue` also gates the whole app behind `AuthGate.vue` whenever `useAuth().isAuthenticated` is false — signing out routes back there via `useSync.ts`'s `clearAll()`.

**Styling**: Tailwind v4 (via `@tailwindcss/postcss`, configured in `postcss.config.js` — there is no `tailwind.config.js`, v4 is CSS-first) for layout/spacing utilities, combined with inline `style` bindings referencing CSS custom properties defined in `src/style.css` (`--ink`, `--paper`, `--accent`, `--money-in`, `--money-out`, etc.) for the dark color scheme. Follow this mix rather than adding Tailwind color classes or a `tailwind.config.js` theme — colors are meant to stay centralized in the `:root` variables.

**PWA**: configured via `vite-plugin-pwa` in `vite.config.ts` (`registerType: 'autoUpdate'`). Manifest name/icons/theme colors are defined there, not in `index.html` or `public/manifest.json`.

**Backup/restore**: `exportCsv()` in `useLedger.ts` is the primary backup path — one row per transaction (`date, type, wallet, label, note, amount, planned`), wallet name resolved from `walletId` via the `wallets` from `useWallets()`, sorted by date; it's read-only (no CSV import). `exportData()`/`importData()` round-trip transactions _and_ wallets as JSON (`{ exportedAt, transactions, wallets }`) and are the only round-trippable format; `App.vue`'s Settings panel surfaces CSV export as the main button and tucks JSON export/import under an "Advanced" `<details>`. `importData(json)` is always additive against Supabase — it inserts anything not already present locally (by id for transactions, by id-or-name for wallets, via `useWallets.ts`'s `importWallets`) and throws if any row failed to insert, so partial success still surfaces as an error in `App.vue`'s `importMessage`.
