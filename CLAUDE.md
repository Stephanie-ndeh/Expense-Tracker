# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Reckon" — a single-user expense/lending/savings tracker built as an installable PWA, backed by Supabase (Postgres + email/password auth). Everything — wallets, transactions, categories, people, and the currency/display-name profile — lives in Supabase, scoped per-user via Row Level Security (`supabase/schema.sql`); the one thing in `localStorage` is the `theme` display setting (`useSettings.ts`), deliberately device-local rather than synced — see "Theming" below. See `README.md` for the product description.

## Commands

```bash
npm install
npm run dev       # vite dev server
npm run build     # vue-tsc -b (typecheck, project-references build) then vite build
npm run preview   # serve the production build locally
npm run lint      # eslint . (flat config in eslint.config.js)
npm run format    # prettier --write . (config in .prettierrc.json)
```

There is no test suite — `npm run build` (via `vue-tsc -b`) is the strictest correctness check available: `noUnusedLocals`, `noUnusedParameters`, and `noFallthroughCasesInSwitch` are all enabled in `tsconfig.app.json`, so unused variables/params fail the build, not just warn. `npm run lint`/`npm run format` catch style/correctness issues `vue-tsc` doesn't (e.g. unused-but-typed-away mistakes, Vue template rule violations). Run `format`, then `lint`, then `build`, in that order, before every commit — see "Git workflow" below.

**Vue template pitfall**: an inline event handler with more than one statement (e.g. `@click="a = 1\nb = 2"`) relies on semicolons as statement separators; this repo's Prettier config has `"semi": false`, which strips those semicolons from template expressions too and breaks the Vue compiler. Avoid multi-statement inline handlers — call a method defined in `<script setup>` instead (e.g. `@click="cancelDelete"` with `function cancelDelete() { ... }`), which is immune to this and matches the existing style in `AddEntry.vue`/`App.vue`.

## Git workflow

Each phase/task gets its own feature branch off `develop` — never commit directly to `develop` or `master`.

1. `git checkout develop && git pull`, then `git checkout -b <phase-name>` (e.g. `phase-1-swipe-actions`).
2. Implement the phase.
3. Before committing, run in order and fix everything: `npm run format`, `npm run lint`, `npm run build`.
4. Commit the phase's changes on the feature branch.
5. Push the feature branch (`git push -u origin <phase-name>`) — do not merge it.
6. The user merges the branch into `develop` manually on GitHub.
7. Once merged, `git checkout develop && git pull` to sync.
8. Before creating the next phase's branch, ask the user for explicit authorization to delete the just-merged branch (local, and remote if pushed). Only delete after they say yes; if they say otherwise, leave it. Never delete it unprompted.
9. Create the next phase's branch.

## Architecture

**State: module-level reactive singletons, not Pinia.** There is no state-management library dependency. `useLedger.ts`, `useWallets.ts`, `useCategories.ts`, `usePeople.ts`, `useTodos.ts`, `useAuth.ts` and `useSettings.ts` all follow the same shape: a `reactive()` object created once at module scope, and the exported `use*()` function just returns computed/methods closing over that shared state. Every component that calls `useLedger()` shares the _same_ transactions array — there is no per-instance state and no store plugin. All four are now a pure in-memory mirror of Supabase — nothing is written to `localStorage`.

**Data lives entirely in Supabase — mostly Supabase-first, except four transaction mutations which are offline-capable.** `profiles`, `wallets`, `categories`, `people`, `transactions`, and `todos` tables (`supabase/schema.sql`) are the sole source of truth, scoped per-user via Row Level Security. Every mutation in `useWallets.ts`/`useCategories.ts`/`usePeople.ts`/`useSettings.ts`/`useTodos.ts` (`addWallet`, `renameWallet`, `removeWallet`, `findOrCreateCategory`, `findOrCreatePerson`, `updateCurrency`, `addTodo`, `setDone`, `removeTodo`, etc.) is `async` and strictly Supabase-first: it awaits the Supabase call first and only updates local reactive state on success, then throws on failure so the calling component can surface an error (see `AddEntry.vue`, `WalletTabs.vue` for the try/catch + inline-error-text pattern). **`useLedger.ts`'s `addTransaction`/`updateTransaction`/`removeTransaction`/`markSettled` are the one exception** — see "Offline-capable transaction mutations" below. `useSync.ts` owns the login/logout lifecycle: `loadAll()` first replays any offline-queued transaction mutations (`flushPendingTransactions()`, if online), then fetches everything fresh from Supabase (wallets, transactions, and `todos` filtered to `deleted_at is null`, plus the profile via `useSettings.ts`'s `loadProfile()`) and **replaces** local state outright (no merge — the server is authoritative), called on sign-in and then on focus/online; `clearAll()` empties local state — including resetting currency back to the default, and clearing the offline queue — on sign-out. That sign-out clear is what prevents one account's data (and any still-unsynced offline edits) from bleeding into the next account signed into the same browser.

**Offline-capable transaction mutations** (`useLedger.ts`, `src/lib/offlineQueue.ts`): `addTransaction`/`updateTransaction`/`removeTransaction`/`markSettled` check `navigator.onLine` first. Online: unchanged Supabase-first behavior. Offline: the change applies to local state immediately (rows touched are flagged `pendingSync: true` — a client-only field, never sent to or read from Supabase) and the mutation is appended to a small hand-rolled IndexedDB queue (`offlineQueue.ts` — no new dependency) instead of throwing. Editing or deleting a row that's itself still only a queued, never-synced `add` rewrites or cancels that `add` directly (`enqueueTransactionMutation()`) rather than stacking a pointless entry for an id Supabase has never seen; a newer queued update also supersedes a stale one for the same id. `flushPendingTransactions()` replays the queue in insertion order against Supabase, continuing past individual failures (one bad item can't block the rest) and returns a `{ succeeded, failed }` summary — `useSync.ts` calls it at the start of every `loadAll()`, and `App.vue`'s Settings panel shows `pendingSyncCount` and any `queueError` from the last flush. **Scope is deliberately narrow**: transfers, to-dos, wallets, categories/people, and the profile/currency setting are not offline-capable — those still require a connection. One related edge case: `findOrCreateCategory`/`findOrCreatePerson` fail fast with a clear "You're offline" message if the typed name has no local match (would otherwise attempt a doomed network insert) — existing categories/people still resolve fine offline since that lookup is already local-only.

**Soft delete, not hard delete.** `transactions` and `wallets` have a `deleted_at timestamptz` column (`supabase/migrations/004_soft_delete.sql`). `removeTransaction`/`removeWallet` `UPDATE … SET deleted_at = now()` instead of `DELETE`, then splice the row out of local state; `useSync.ts`'s `loadAll()` is what keeps soft-deleted rows out of the app by filtering `.is('deleted_at', null)` on every fetch. Any new query against these tables must apply the same filter, or deleted rows will reappear.

**IDs and timestamps**: new `wallets`/`transactions` ids are generated client-side with `crypto.randomUUID()` (the `id` columns stay plain `text`, so pre-existing non-UUID ids are untouched). `created_at` is `timestamptz` in the database (the original bigint epoch-ms columns were renamed to `created_at_ms` and kept as an untouched fallback — see `supabase/migrations/007_timestamptz_created_at.sql`); the app still works with it as a epoch-ms `number` everywhere else — `rowToTransaction`/`rowToWallet` convert the ISO string to a number on read (`new Date(r.created_at).getTime()`), and the insert helpers convert back on write (`new Date(t.createdAt).toISOString()`).

**Categories & people**: `categories` (`id`, `user_id`, `name`, `kind: 'expense' | 'income'`) and `people` (`id`, `user_id`, `name`, `phone`) are separate tables, each with a case-insensitive unique name per user (per `kind` for categories), managed by `useCategories.ts`/`usePeople.ts` — the same module-level-singleton shape as `useWallets.ts`, loaded/cleared by `useSync.ts` alongside everything else. `transactions.category_id`/`person_id` are nullable foreign keys; `label` is still what's displayed and what `personSummaries`/`owedToYou`/`categoryBreakdown` group by in `useLedger.ts`, but it's now always resolved to a category/person's canonical spelling (see below), so same-ish labels no longer split into separate buckets by casing.

**Category/person find-or-create** (`AddEntry.vue`): the category field (expense/income) and the person field (lend/repay) are plain `<input list="...">` elements backed by a `<datalist>` of suggestions — `useLedger.ts`'s `suggestedCategories(kind)`/`suggestedPeople()` return that type's categories/people sorted most-used-first, counted from `category_id`/`person_id` occurrences in `state.transactions` (not full-text label matching). On submit, the typed text is resolved via `useCategories.ts`'s `findOrCreateCategory(name, kind)` / `usePeople.ts`'s `findOrCreatePerson(name)`: a case-insensitive match against the already-loaded local list first (no network round-trip), falling back to an insert (racing a duplicate-key error is handled by re-querying rather than throwing, since this is "find or create", not a user-facing duplicate check) — the resolved row's `id` and canonical `name` are what get saved as `categoryId`/`personId` and `label`. `save`/`withdraw` labels remain plain free text, untouched by any of this.

**Integrity constraints** live in `supabase/migrations/005_integrity_constraints.sql`, `006_amount_positive_check.sql`, `010_transfers.sql`, and `011_debt_types.sql`: a composite FK ties `transactions(wallet_id, user_id)` to `wallets(id, user_id)`; `transactions.type` has a `check` listing the current `TransactionType` values — **adding a new transaction type requires a migration that drops and recreates `transactions_type_check`** with the wider list, or inserts will fail; `transactions.amount` must be `> 0`; a partial unique index guarantees at most one `is_default = true` wallet per user (excluding soft-deleted ones); and a `check` ties `transfer_id`'s presence exactly to `type in ('transfer_out', 'transfer_in')`.

**Domain model** (`src/types/transaction.ts`): a single `Transaction` shape covers ten transaction types (`expense`, `income`, `lend`, `repay`, `save`, `withdraw`, `transfer_out`, `transfer_in`, `borrow`, `payback`). `TYPE_META` is the lookup table that drives everything derived from a type: display verb, sign (+1/-1) for balance math, the placeholder hint for the `label` field, and which `group` (`cash` | `lending` | `savings` | `transfer` | `debt`) it belongs to. Adding a new transaction type means extending this union and `TYPE_META`, not branching on the type string elsewhere — most of `useLedger.ts` is written generically against `TYPE_META[t.type].sign/group`.

**Money you owe** (`borrow`/`payback`, `group: 'debt'`): the mirror image of `lend`/`repay` — `borrow` (sign `+1`) is money coming in that you owe someone, `payback` (sign `-1`) is money going out that reduces that debt. Both are person-linked exactly like `lend`/`repay` (same `findOrCreatePerson` flow in `AddEntry.vue`, same `suggestedPeople()` suggestions, both required rather than falling back to a generic label). `balance` adds `+ debt_sum` as one more additive group term (borrowing increases your spendable cash, paying it back decreases it) — kept separate from the per-person obligation tracking. `personSummaries` in `useLedger.ts` now groups all four people-linked types by person, producing two independent net figures per person: `netOwed` (`lent - repaid`, what they owe you) and `netOwe` (`borrowed - paidBack`, what you owe them) — `owedByYou`/`totalOwedByYou` mirror the existing `owedToYou`/`totalOwedToYou` for the "You owe" summary card. `plannedSpend` counts planned `payback` as a future outflow (like planned `expense`/`lend`), but not planned `borrow` (an inflow). `PeopleView.vue` shows whichever of the two directions actually has activity for each person, including the (normally-zero) overpaid case for either direction.

**Transfers between wallets**: a transfer is two ordinary `transactions` rows — one `transfer_out` (sign `-1`) on the source wallet, one `transfer_in` (sign `+1`) on the destination wallet — sharing a `transfer_id`. This is why `balance` just adds `+ transfer_sum` as one more group term, the same way `lending` is added: whichever leg is in scope for the active wallet correctly moves that wallet's balance, and when both legs are in scope (the 'All' view) they cancel to zero with no special-case code. Each leg's `label` is the _other_ wallet's name (set programmatically by `addTransfer()`, never typed by the user). `monthlyTrend`/`categoryBreakdown`/`monthComparison`/`thisMonthSpend` only match specific other types, so transfers are automatically excluded — no filtering code needed for that. `useLedger.ts`'s `addTransfer()`/`updateTransfer()`/`transferSibling()` are the transfer-specific API (wallets aren't reassignable via `updateTransfer` — delete and recreate instead); `removeTransaction()`/`markSettled()` are transfer-aware internally (they check the row's `transferId` and, if set, act on both rows via a single `.eq('transfer_id', id)` statement instead of `.eq('id', id)`), so every existing call site keeps working unchanged. Pairing integrity has no traditional FK (there's no parent table to point at — just two sibling rows) — it's enforced by a CHECK constraint (`transfer_id` presence) plus doing the multi-row writes as single atomic Postgres statements (one bulk `.insert([outRow, inRow])` for creation, one grouped `.update(...).eq('transfer_id', id)` for edit/delete) rather than two independent calls. `AddEntry.vue` shows "Transfer" as one type option with its own From/To-wallet sub-form; editing a transfer shows its wallets as read-only (can't reassign) with amount/date/note/planned still editable, and switching an existing entry's type into/out of `'transfer'` is disabled via `canSelectType()`.

**Money to-do list** (`useTodos.ts`, `todos` table): a to-do is a lightweight, mostly-optional template — only `title` is required; `amount`, `type` (same 8 non-transfer types as recurring rules, nullable), `dueDate`, and `walletId` are all nullable, and `wallet_id` has no `not null` on the composite FK (a null `wallet_id` trivially satisfies it, unlike on `transactions`/`recurring_rules` where the wallet is mandatory). To-dos are entirely separate from `transactions` — nothing here feeds `balance` or any aggregate until a to-do is actually turned into a transaction. Ticking a to-do's checkbox (`setDone(id, true)` in `useTodos.ts`) always marks it done immediately; _if it has an amount_, `TodosView.vue`/`UpNext.vue` (Home) additionally emit a `log` event carrying `{ type, amount, label: title, walletId }` up to `App.vue`, which stores it in a `todoPrefill` ref and opens `AddEntry` with its new `prefill` prop. `prefill` is deliberately a separate prop from `editing` — it only seeds `form`'s initial values (falling back to `AddEntry`'s own defaults for anything the to-do didn't set, e.g. type defaults to `'expense'`), so submission still goes through the normal **create** path (`addTransaction`) with every field still freely editable, rather than being locked the way editing an existing transaction is. Closing that `AddEntry` without saving leaves the to-do done but creates no transaction — that's what makes the prefill an "offer", not a requirement.

**To-dos screen** (`TodosView.vue`, Phase D5): pending to-dos are split into three date-based groups — Overdue (`dueDate` in the past), This week (`dueDate` within the next 6 days), Later (no date, or further out) — each rendered only when non-empty; a filter chip row (All / With money / Done) narrows which pending to-dos show (or, for Done, swaps to a flat completed list) without affecting anything else. The "Money due this week" card sums Overdue + This-week amounts (not Later) and shows `balance - thatAmount` as "After that you'd have" — both are always computed from the full to-do list regardless of the active filter chip. The square checkbox on each row and the "Log it" pill (shown only when the to-do has an amount) both call the same existing `toggle()` — "Log it" is just a second, more visible entry point for that one action (mark done, then offer the prefill), not a separate flow; this avoids needing `AddEntry` to distinguish "saved" from "cancelled" on close. Row subtitles use a weekday name for anything within ±6 days of today (`formatRelative()`), a short date otherwise, and append amount/wallet name when set — the old per-row type verb isn't shown anymore.

**Wallets** (`src/types/wallet.ts`): every transaction has a `walletId`. `WalletSwitcher.vue` (top of Home) is a dropdown button — avatar-initial chip + the active wallet's name + "All wallets" — that drives the shared `activeWalletId` ref, which every `useLedger()` consumer filters against; it's selection-only. Add/rename/delete live separately in `MeView.vue`'s "Wallets" list (vertical card, not a tab row) — `WalletTabs.vue`, which used to do both jobs, was deleted in Phase D2 when they split. Exactly one wallet per user has `isDefault: true` (auto-created as "Personal" by `useSync.ts`'s `loadAll()` the first time a user's wallet list comes back empty) — it can be renamed but can't be deleted. `addWallet`/`renameWallet`/`removeWallet` in `useWallets.ts` enforce, respectively: no duplicate names per user (case-insensitive, backed by a unique index in `supabase/schema.sql` as well as a client-side check — `renameWallet` excludes the wallet's own id from that check), the same duplicate-name rule when renaming (requires the `wallets_update_own` RLS policy from `supabase/migrations/001_wallets_update_policy.sql`), and no deleting a wallet that still has transactions in it (blocked, not cascaded — the user has to empty it first).

**Profile/currency** (`useSettings.ts`): `settings.currency` is now backed by the `profiles` table (`id = auth.users.id`, one row per user, lazily created defaulting to `'FCFA'` the first time `loadProfile()` runs with no existing row) instead of `localStorage`. The currency `<input>` in `MeView.vue` still uses `v-model` for snappy typing, but only persists on `@change` (blur/commit) via `updateCurrency()` — not on every keystroke — since each save is now a network round-trip; a failed save surfaces inline via `currencyError` in `MeView.vue` without reverting the input.

**`planned` is the "hasn't happened yet" flag**, not a separate list — a transaction is either `settled` (`!planned && date <= today`) or `upcoming` (`planned || date > today`). Balance, savings, and monthly aggregates are all computed only from `settled`; `upcoming` feeds the "coming up" UI. Keep this filter (not a boolean split into two arrays) when adding new derived views.

**`useLedger()` is the single source of derived data** — balance, savings, per-person owed amounts, monthly trends, category breakdowns, month-over-month comparisons, search/filtering, and JSON export/import all live here as computed properties or functions over the one `state.transactions` array. Components (`BalanceHero`, `SummaryCards`, `ThisMonthCard`, `PeopleView`, `TrendsView`, `AllActivityView`, `RecentActivity`, `UpNext`, etc.) are thin — they call into this composable rather than recomputing aggregates themselves. When adding a new summary/view, prefer adding a computed/function here over duplicating filter/reduce logic in a component.

**Home** (`HomeView.vue`, Phase D3): composes, in order, `WalletSwitcher`, `BalanceHero`, `SummaryCards` (now a 3-column strip — Owed to you / You owe / Savings only, no 4th "coming up" tile), `ThisMonthCard`, `TransactionFeed` ("Coming up" — unchanged), `UpNext`, and `RecentActivity` (now trimmed to the last 4 via `recentActivity` in `useLedger.ts`, not 5). `ThisMonthCard.vue` reuses `monthComparison` to show "Spent X · received Y. {Up/Down}N% on {last month}." and links into Activity's Insights tab — it replaces the old `TrendChart.vue` mini bar-chart teaser, which is deleted (Insights' own chart is separate, inline in `TrendsView.vue`). `UpNext.vue` replaces `UpcomingTodos.vue` (also deleted): it merges pending to-dos and `useLedger()`'s `upcoming` transactions into one date-sorted list and shows just the 2 soonest — tapping an item's checkbox square calls `setDone`/`markSettled` depending on which kind it is. The warm gold-tinted surface `ThisMonthCard.vue` sits on isn't part of the core D1 token table — two extension tokens, `--accent-surface`/`--accent-surface-line`, were added to `style.css` (dark+light) specifically for it.

**Activity** (`ActivityView.vue`, Phase D4): owns the "Activity" title and the List/Insights segmented toggle, taking an `initialTab` prop so Home's shortcuts (`ThisMonthCard` → Insights, `RecentActivity` → List) land on the right tab — otherwise the tab is local state, reset to List whenever the bottom nav's Activity icon is tapped directly (see `App.vue`'s `navigate()`). It renders `AllActivityView.vue` (List) or `TrendsView.vue` (Insights).

**List** (`AllActivityView.vue`): a search input plus a "Filters" button (badge = count of active filter dimensions) opens a sheet with the same fields as before — type, wallet, category/person (`label`), date range (presets + manual), amount range — `filterActivity(filters)` in `useLedger.ts` itself is unchanged (deliberately unscoped by the shared `activeWalletId`; `query` substring-matches `label`/`note`; `type`/`walletId`/`label` are exact matches, `'all'` meaning unfiltered; `label` is matched against the merged, deduped set of category + people names). Active filters surface as removable chips below the search row (each clears just that one dimension). `activityTotal(items)` sums `TYPE_META[type].sign * amount` over whatever's filtered, shown in a top "N entries · Net ±X" bar; results are grouped by day (a local `groups` computed, not in `useLedger.ts` — this is presentation-only grouping on top of the already-correct filtered/sorted list), each day showing a label (Today/Yesterday/date) and that day's own net total via `activityTotal`.

**Insights** (`TrendsView.vue`): a month switcher (next-month arrow disabled once on the current month) drives `monthComparison(offset)`/`categoryComparison(offset)` in `useLedger.ts` — both were converted from hardcoded this-vs-last-month `computed`s into offset-taking functions (matching the existing `monthlyTrend(months)`/`categoryBreakdown(offset)` pattern) so Insights can page through any month; `ThisMonthCard.vue` on Home calls `monthComparison(0)` to keep its original fixed behavior. Spent/Received tiles color their vs-last-month delta by outcome, not just direction — `--money-in` for a favorable swing (spend down, income up), `--warn-text` for an unfavorable one (not `--money-out`, matching `design/Insights.dc.html`'s choice). The 6-month In/Out bar chart is unchanged (`monthlyTrend(6)`). "Where it went" bars size proportionally to the top category's amount (not an absolute scale), and a tip card appears specifically when `categoryComparison`'s top entry is label `'Other'`. The old "Total saved so far" line is gone — not in this design, already shown on Home's 3-column strip.

**`App.vue` is a hand-rolled router with a persistent shell**: a single `view` ref (`'home' | 'activity' | 'todos' | 'me' | 'appearance'`) switches the body content shown above a fixed `BottomNav.vue` (Home · Activity · centre gold "+" · To-dos · Me, per `design/DESIGN.md`'s structure notes) — the nav itself stays mounted across every view except `'appearance'`, which is a pushed sub-screen (reached from `MeView.vue`, shown with its own back chevron instead of the bottom nav). `'trends'` no longer exists as its own view: the old `TrendsView.vue` is now shown as an "Insights" tab alongside `AllActivityView.vue`'s "List" tab inside `ActivityView.vue` (see "Activity" above) — `HomeView.vue`'s `ThisMonthCard` ("open-insights") and `RecentActivity` ("open-activity-list") emits both bubble up through `HomeView` to `App.vue`, which lands on `view = 'activity'` with its `activityTab` ref passed down as `ActivityView`'s `initialTab` prop. Modals (`AddEntry`, `PeopleView`) are still boolean-flag overlays rather than routes; the old inline Settings modal is gone entirely — its content (currency, sync status, backup/restore) now lives in `MeView.vue`. There's no vue-router. Ahead of the router, `App.vue` also gates the whole app behind `AuthGate.vue` whenever `useAuth().isAuthenticated` is false — signing out (now triggered from `MeView.vue`) routes back there via `useSync.ts`'s `clearAll()`.

**Styling**: Tailwind v4 (via `@tailwindcss/postcss`, configured in `postcss.config.js` — there is no `tailwind.config.js`, v4 is CSS-first) for layout/spacing utilities, combined with inline `style` bindings referencing CSS custom properties defined in `src/style.css` (`--bg`, `--surface`, `--line`, `--nav`, `--text`, `--text-dim`, `--money-in`, `--money-out`, `--savings`, `--accent`, `--accent-text`, `--on-accent`, `--warn-bg`, `--warn-text`, `--accent-surface`, `--accent-surface-line`). Follow this mix rather than adding Tailwind color classes or a `tailwind.config.js` theme — colors are meant to stay centralized in the token definitions. Font is Manrope (400–800); `font-variant-numeric: tabular-nums` is set globally on `body`, so money figures don't need a monospace font or a `.font-mono`/`tabular-nums` class.

**Theming** (`src/style.css`, `useSettings.ts`): tokens come in a dark and a light set. Dark is whichever applies first: a `@media (prefers-color-scheme: dark)` block overridden by an explicit `:root[data-theme="dark"]` block; `:root` alone (no `data-theme`, light OS preference) is the light baseline, with `:root[data-theme="light"]` as its explicit-override twin. `useSettings.ts` exposes `theme: Theme` (`'system' | 'light' | 'dark'`, default `'system'`) and `setTheme()` — the choice is persisted to `localStorage` (`reckon.theme.v1`), not Supabase, since it's a device preference, not account data; `clearSettings()` (called on sign-out) deliberately leaves it untouched. `setTheme()` sets or removes `data-theme` on `<html>` and updates `<meta name="theme-color">` to match the resolved theme; a `prefers-color-scheme` `matchMedia` listener re-applies live when the setting is `'system'` and the OS theme changes. Two rules on top of the token table: the balance figure is always `--text` regardless of sign (an overspent wallet gets a small `--warn-bg`/`--warn-text` pill instead of recoloring the number itself), and `--accent` (gold) is reserved for actions/selection, never for a money figure — a savings amount uses the dedicated `--savings` token instead. Because gold itself doesn't change between themes, text/icons drawn on an accent-filled background use the fixed `--on-accent` token (not `--text`, which would go light-on-gold in light mode); destructive buttons (money-out-filled) use the normal theme-reactive `--text`/`--bg`, since money-out's two theme values already contrast correctly against both.

**PWA**: configured via `vite-plugin-pwa` in `vite.config.ts` (`registerType: 'autoUpdate'`). Manifest name/icons/theme colors are defined there, not in `index.html` or `public/manifest.json`.

**Backup/restore**: `exportCsv()` in `useLedger.ts` is the primary backup path — one row per transaction (`date, type, wallet, label, note, amount, planned`), wallet name resolved from `walletId` via the `wallets` from `useWallets()`, sorted by date; it's read-only (no CSV import). `exportData()`/`importData()` round-trip transactions _and_ wallets as JSON (`{ exportedAt, transactions, wallets }`) and are the only round-trippable format; `App.vue`'s Settings panel surfaces CSV export as the main button and tucks JSON export/import under an "Advanced" `<details>`. `importData(json)` is always additive against Supabase — it inserts anything not already present locally (by id for transactions, by id-or-name for wallets, via `useWallets.ts`'s `importWallets`) and throws if any row failed to insert, so partial success still surfaces as an error in `App.vue`'s `importMessage`.
